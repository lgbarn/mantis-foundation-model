Training-First MantisV2 LP-LoRA Plan

Objective: cheaply test whether preparing MantisV2 task heads before LoRA improves the existing NextLeg foundation training. This plan starts with training, not a new downstream, RL, walk-forward, Optuna, or multi-timeframe framework.

Why this is the next experiment

The NeurIPS 2024 LP-FT paper gives a defensible mechanism for head warm-up: an already useful task head can reduce destructive early changes to pretrained features. Its evidence is strongest for linear probing followed by full fine-tuning under cross-entropy classification. Our NextLeg task uses candle MSE plus leg SmoothL1 and attention LoRA, so it is a hypothesis here, not a result.

Therefore the first test is an A/B training pair, not a six-cell matrix and not a claim that LP-LoRA is best. The current code already supports both modes and phase-resumable warm-start training.

Only required preparation

  1. Copy mantis-v2/configs/nextleg-runpod-cuda-bundled-r5-v1.toml into two new immutable configs.
  2. Give each a distinct run name and artifact root. Keep allow_overwrite = false.
  3. Set both data.intervals to ["1min", "3min", "15min"].
  4. For A, set model.mode = "lora_r8_alpha16", remove the [adaptation] section, set epochs = 50, and retain max_steps_per_epoch = 200 for a 10,000-update ceiling.
  5. For B, retain model.mode = "lora_r8_alpha16_head_warmstart" and [adaptation] with warm_start_updates = 2000, total_updates = 10000, lora_rank = 8, and lora_alpha = 16.
  6. Keep every upstream pin, corpus-manifest hash, target setting, and numerical tolerance unchanged from the CUDA template.

The script then writes one immutable, non-promoting screen-decision.json after verifying both exports and their common provenance. Each training command resumes only its own provenance-checked run. Do not start another command using either run identity.

Decision after seed 42

The update budget is compute-matched, not LoRA-step-matched: A has 10,000 LoRA updates while B has 2,000 head-only plus 8,000 LoRA updates. That allocation is the hypothesis under test and is reported in checkpoint provenance. Compare immutable training and export receipts only. B advances only if it has a strictly lower best validation total loss than A, no regression in either candle or leg validation loss, and both exports pass native-to-safetensors parity. A single seed is a screening result, not a model-selection claim.

  • B wins: run the same paired A/B cells for seeds 43 and 44. That is four more training cells, still no downstream or RL work.
  • A wins or result is mixed: stop LP-LoRA. Do not add full fine-tuning, RL, or new timeframes merely to rescue the hypothesis.
  • Paired three-seed B wins: choose the training method for the next separately approved downstream experiment. Only then evaluate a full-finetune comparison if the expected value justifies its cost.

I/O protocol for the next Pod

Use the network volume as persistent, immutable storage. Use the Pod's local ephemeral disk for the active working set. RunPod documents network-volume performance as variable and local container storage as fastest; the prior run made the worst combination by launching five concurrent writers directly against the network volume.

  1. Before renting a GPU, stage the accepted immutable Parquet corpus bundle on the network volume with the S3-compatible API. Data upload is a local-machine or CPU-only task.
  2. At Pod startup, check only free local disk space, then copy the accepted bundle once from /workspace/mantis/inputs/<bundle> to /tmp/mantis/inputs/<bundle>. Do not scan, audit, or otherwise revalidate Parquet on the GPU Pod.
  3. Point both A and B configs at the copied local corpus and its identical manifest hash. Run the paired training cells sequentially on the same Pod so the second cell reuses the local copy.
  4. Keep checkpoints, TensorBoard logs, validated exports, and final manifests under /workspace/mantis/runs for persistence and resume.
  5. For any later embedding diagnostic, write its temporary shards under /tmp/mantis/work/<run-id>, use one writer, hash there, then copy only the final digest directory to the network volume.

Do not copy the corpus separately for A and B. Do not write five embedding arrays concurrently. Do not put the Python environment on the network volume. The working copy and the resolved virtual environment belong on local ephemeral storage; durable inputs and final artifacts belong on the network volume.

Explicitly out of scope

  • 3TF downstream-pipeline refactor.
  • Embedding diagnostics, walk-forward, Topstep simulation, or RL.
  • Optuna, broader hyperparameter sweeps, and new model modes.
  • Adding 5m, 4TF, or cross-ticker changes.
  • Using the reserved holdout for selection.

Evidence and limits

Tomihari and Sato, "Understanding Linear Probing then Fine-tuning Language Models from NTK Perspective," NeurIPS 2024, supports testing head warm-up as a feature-preservation mechanism. It does not establish that LP-LoRA improves MantisV2, time-series models, regression losses, or trading performance. The plan treats it as one paired training hypothesis and demands a result before adding scope.
